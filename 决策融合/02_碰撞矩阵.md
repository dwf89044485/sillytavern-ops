## M1 蒸馏产物形态：知识单元 vs 追问动作 ✅

**A**：按 cangjie 五类提取器切分，产出框架 18 / 原则 110 / 案例 20 / 反例 53 / 术语 34。三重验证的对象是 **18 个 framework**。

**B**：3 个 agent 从"追问技法"角度提取，产出 14 个追问动作。三重验证的对象是 **14 个动作**，每个动作三件套（AI 内部诊断 + AI 外部问法 + 质量门）。

**判定：✅ 可融合互补，这是本次碰撞最大的收益点。**

辨析：

- A 回答的是"教程里有哪些知识值得蒸馏"，B 回答的是"这些知识在对话中长什么样"。两个问题都必须回答，A 只答了前者，B 只答了后者。
- **A 的候选池是 B 没用上的弹药**：B 的 3 个 agent 只读了教程原文，没有 A 的 `counter-examples.md`（53 条失败模式）和 `principles.md`（110 条原则）。这批材料正是 B 的 probe 文件里"质量门"和"禁止事项"该引用的东西。
- **B 的动作池是 A 缺的执行形态**：A 的 11 个 reference 是空容器（只有文件名+一句话描述+触发条件），B 的 13 个动作三件套正是要装进去的内容。

融合方向：保留 A 的五类候选池作为**素材库**，保留 B 的动作三件套作为**成品形态**，并回头用 A 的 counter-examples / principles 补齐 B 的 9 个 probe（B 的每个动作现在只有 2-4 句问法，缺"什么算做错了"）。

### M2-a 🔴 user-info-calibration 的归属

- **A**：独立 skill。依据是三重验证——V2 预测力通过（可诊断"AI 为什么总把抓手腕理解成强制"），V3 独特性通过（"行为翻译手册"是独创概念），trigger 独立且与"帮我写角色"互斥。A 的 `verified.md` 记录了它经历"降级为附录 → 恢复为独立 skill"的完整推翻过程。
- **B**：并入"角色卡设计 skill"（PIPELINE_STATE 待办表 #1 明写包含"用户信息（抢话党/不抢话党）"）。B 没有给论证，只是归类。
- **证据强度**：A 有完整三重验证 + 已否决方案记录，B 只有一行归类。**A 明显更强。**

### M2-b 🔴 B 多出的"角色验证/体检 skill"

- **B 的洞察**："阶段 1 的 6 个基础诊断逻辑可以**反过来**用作检测工具"——检测已有卡的标签化程度、标签打架、泛化外貌、结论式背景、缺失维度。
- **A 的对应位置**：不是 skill，是 char-build-guide 的一个入口。`ARCHITECTURE.md` 第四节列了"E: 校验入口——帮我看看这段写得对不对 → 校验模式，不启动完整引导流程"；`B_SEGMENT` 也写了"用户已有完整角色卡只想微调 → 校验模式"。
- **辨析**：B 的洞察是真的——4 个诊断做成检测器，输入是一整张卡而不是一句回答，输出是问题清单而不是下一个问题，**交互形态完全不同**。但它要过 A 的 trigger 互斥检验，而 A2 Agent2 恰好警告过："『帮我看看』是万能句式，校验入口的信号必须窄化"。所以这条如果独立成 skill，和 char-build-guide 的 trigger 冲突风险很高。
- **需要拍板**：独立成 skill / 留作 char-build-guide 的校验模式 / 推迟到全部 4 个 skill 写完后再评估。

### M2-c 🔴 B 隐含的"角色卡设计 skill"

- **B**：把机制设计（阶段/进化系统/分支路线）、长期性、开场白、用户信息打包成一个 skill——定位是"把塑造好的角色装进可玩的卡里"。
- **A**：开场白"保留在 char-build-guide 内部（构建流程最后一环，trigger 太弱）"；长期性"降级为原则，注入 char-build-guide 收束考量"；用户信息独立成 skill。**A 把 B 的这一个 skill 拆散到了三处。**
- **辨析**：B 的打包有一个 A 没看到的共性——这三样东西都不是"角色是什么样的人"，而是"这个角色怎么被玩"。A 的判断依据是单项 trigger 强度（开场白 trigger 弱、长期性不是独立方法论），B 的判断依据是场景聚合（打包后 trigger 就不弱了："我的角色写好了，怎么让它能玩很久"）。两种拆分逻辑都成立。
- **注意**：A 的 `B_SEGMENT` 发现 5 已经诚实标注了盲区"**角色卡测试与迭代：当前无 skill 覆盖**"——B 的这个 skill 正好落在那个已知缺口上。

## M4 诊断系统精度 ⚠️

**A**：§3.2「深度信号识别」6 行表（纯形容词 / 具体行为不够独有 / 两个以上截然不同行为模式 / 两个特质同一画面打架 / 不知道原因 / 多画面看不出共性 → 各自的追问方向）。无三级判定、无判定树、无正反例、无灰色地带处理。

**B**：4 个诊断，每个 = 一句话原则 + 判定树 + 内容分类 + 灰色地带表 + 正例 4-5 + 反例 4-5 + 教程锚点；外加跨诊断优先级、放大器规则、AI 默认值规则、伪负面识别、方向多样性、结论词清单、瞬间动词 vs 模式动词。

**判定：⚠️ 表面冲突——B 是对 A 的最大单项补充，唯一张力可用一条界线化解。**

张力在哪：A §1.2 明确否决过"穷举判断规则（if-else 状态机）"，理由是"规则越多，AI 越不敢用自己的判断力"。B 的判定树形式上就是 if-else。

化解的界线：**判据可以穷举，流程不可以。**

- A 否决的是**流程规则**（什么时候问什么、下一步走哪），因为对话的边缘情况穷举不完。
- B 提供的是**文本判据**（这句话是不是泛化、这两个标签是不是真打架），判据的输入是一段有限文本，可以穷举。
- 佐证：A 自己的 §4.3.2 质量信号表（A-G 七个信号 + 组合规则 + 明确排除的假信号）形式上和 B 的判定树完全同构。A 从没觉得那违反 §1.2。

另一处小张力：B 说"灰色地带默认走观察——宁可多问一句，不要误判为没问题"，与 A §2.4「追问不是审讯」和 `B_SEGMENT` 发现 7 的"过度追问"风险有轻微冲突。但 B 自己给了刹车（"同时触发多个，只处理优先级最高的 1-2 个，不要一轮追问 3 个问题"），够用。

**注意 A 和 B 的诊断是两个层级，不是替代关系**：A 的 §3.2 判"用户现在在哪个深度、该往哪推"，B 的 4 诊断判"用户刚说的这句话质量够不够"。融合后应该同时保留，嵌套使用。

## M5 流程与阶段模型 ⚠️ + ✅

**A**：三职责阶段（接住用户找起点 → 追问循环 → 深化+收束）+ E 段三步（入口与素材初始化 / 追问引擎循环 / 条件深化与收束组装），完成标准全部锚定文档产物。

**B**：五阶段线性主干（入口分流 → 基础身份轻量 → 性格质地主阶段 → AI 可执行性 → 意象 → 整理输出）+ 三类信号在主阶段内持续检测触发深度分支 + 6 条运行规则。

**判定：⚠️ 结构冲突但可融合，且 B 补了 A 的三个缺环。**

结构辨析：

- A 按**职责**切，因为 cangjie 的 E 段要求每步有可判断的完成标准，A 的 `E_SECTION_DESIGN` 决策 1 明确否决了"按时间阶段切"（"中间没有可判断的完成标准"）和"按教程七层切"。
- B 按**时间阶段**切，正是 A 否决过的维度。
- 但 B 的五阶段其实是 A 的"内部模式激活顺序"的时间轴投影——A 的 `ARCHITECTURE.md` 第三节列的 7 种内部模式（基础信息/调色盘/多面性/混色/核心人格层/二次解释/意象），按默认顺序排开就是 B 的五阶段。
- **融合方向**：以 A 的三职责为 E 段骨架（保住 cangjie 合规），把 B 的五阶段降级为"内部模式的默认推进顺序"写在步骤 2 内部。两者不打架。

**B 补的三个缺环（✅ 直接采纳）：**

1. **「AI 可执行性」建模成独立阶段**。A 把二次解释写成"每个深度层完成后追加"，没有把它建模成一个有独立完成标准的环节。**"常用语 / 她绝对不会怎么说话"在 A 里只躺在 `question-bank.md`（24 问第六组）里当弹药，从没被提升为一个必经环节**——而它恰恰是"AI 能不能演对"的直接抓手。B 的 #13 误读预判追问在三重验证里 V3 独特性评为**最强**（"任何非 AI 语境的写作教练都不会想到预判 AI 会怎么误读你的角色"）。
2. **「意象总是尝试」**。精确说：A 的权威主文档 `CHAR_BUILD_GUIDE_DESIGN.md` §4.4 收束只说"整理为结构化记录 + 问还有什么没写到"，**没提意象**；意象在 A 的主文档里只出现在快速路径 G3 第五步、L4 构建区依赖链、§12.8 文档骨架；A 的 11 个 reference 里**没有 imagery 文件**。（参考文档 `E_SECTION_DESIGN.md` 的 E 段骨架里有"意象已探索或跳过均有记录"，但那是被部分取代的历史输入。）B 的决策 11 明写"意象总是尝试，AI 主动提炼并提议，用户觉得对就留，不对就不要"。**血脉 0 的 char-creator SKILL.md 写的也是"意象（必须尝试，允许跳过）"——两条独立血脉都写死了，A 的主文档是唯一没写死的。**
3. **「基础身份轻量处理」**。B 的决策 10 明确"用户带完整信息来就提取确认，不强制重走"。A 的 E 段步骤 1 有"已有角色卡→解析映射到素材区"，但没有"轻量"这个定位，也没有对"基础身份"这一层单独设约束。

**A 独有、B 完全没有（✅ B 无冲突，全盘吸收）**：MVC 三层判读 + 质量信号表 A-G、降级链条（镜子→脚手架→推演→溯源→降级）、卡住根因诊断四阶段、引导升级阶梯四级、示范边界三硬约束、标签优先 G5、情绪串防御性纠偏 G9、方向变更回步骤 1、多入口路由五类、快速路径全套。

## M6 文档状态标记 🔴

**A**：素材区条目三档状态（🔄 正在深挖 / 📌 已记录未深挖 / ✅ 已消化）+ 归档区推翻记录 + 构建区依赖链注释。维度是**挖掘进度**。

**B**：最终文档必须区分三类内容——**用户明确确认的 / AI 根据对话推论的 / 用户还没决定的**，"不把推论当事实"（运行规则 6）。维度是**内容可信度**。

**判定：🔴 真冲突——不是符号打架，是"AI 推论能不能进文档"这个问题上给了互斥答案。**

- A 的机制是"**未确认就不进构建区**"：L10 自然语言投影确认要求每个构件写入后投影给用户，按 E 段决策 4 的确认信号定义回应；敷衍不算确认。A 的三档状态里**没有"AI 推论未裁决"这一档**。
- B 的机制是"**进但打标**"：AI 推论可以在最终文档里，只要标清楚它是推论。
- 血脉 0 站 B 这边："推演候选标注槽位（如 →核心人格层·防御机制）"。

两者各有代价：

- A 的做法保证文档里全是用户认可的东西，代价是 AI 推演过的、用户没明确表态的内容会丢失。
- B 的做法保留全部推演轨迹，代价是文档里混着未验证内容，下游（写卡、一致性验证）要额外分辨。

→ 收敛到拍板单 **C7**

## M7 术语暴露策略 ✅

**A**：术语不出现在 I 段（I_SECTION 三方一致），是 AI 的内部诊断地图；I 段必须用执行语言（"追问用户哪个特质是一直在的"）不用教学语言（"底色是……"）；术语可在 E 段作为 AI 内部标签。

**B**：同一结论（决策 3、决策 8、架构约束"不用术语，不预设用户懂任何东西"）。

**判定：✅ 完全一致，且 B 提供了 A 缺的执行形态。**

A 只有原则，B 把它做成了**文件结构约束**：每个 probe 文件强制分两节——「AI 内部诊断」和「AI 对用户的外部问法」，并明说"诊断是 AI 内心的判断，用户看不到；外部问法是 AI 实际说的话，不暴露方法论、不用术语"。

原则容易被写作时忘记，结构约束不会。融合时把这个两节结构作为**所有 reference 文件的强制模板**。

（注：B 的 probe 文件名直接用了方法论名——probe-faces=多面性、probe-core=核心人格层、probe-moments=混色。那是内部文件名，用户看不到，不违反本条。）

## M8 三重验证的四个交叉点 ✅

两套用了**同一套验证标准**（V1 跨域佐证 / V2 预测力 / V3 独特性），但验证对象不同（A 验框架，B 验动作），所以结论本身不冲突。有四处交叉：

| 交叉点 | A 的判决 | B 的判决 | 性质 |
|---|---|---|---|
| **长期性设计** | f16 降级为原则（V3 不通过，"游戏设计常识"） | 淘汰（V1 不通过，只在教程 6 出现），归未来的角色卡设计 skill | ✅ **独立收敛一致**——两条独立支线用不同理由到达同一结论，可信度最高，锁定 |
| **遮名测试 / 删行测试** | f17+f18 降级为通用技法，"注入 GLOSSARY + 所有 skill 的 E 段自检" | 做成泛化检测判定树的 Step 1（遮名测试）+ 基础信息完成标准（删行测试） | ✅ 互补，**B 的落地更具体**——A 只说"注入自检"，B 给了可执行的判定树 |
| **世界观** | f08 → 独立成 `worldbook-config` skill（ABC 分类 + 蓝绿灯配置） | 用户捞回为 `probe-world`（"不构建完整世界，只锚定到够让角色站住"） | ⚠️ 表面冲突，实为分工——A 的 `ARCHITECTURE.md` 第五节已写"简单 AB 类 char-build-guide 内部处理，复杂 C 类路由到 worldbook-config"，**B 的 probe-world 正是那个"内部处理"的操作手册** |
| **NSFW** | 几乎没有（只在 f02 的 V1 跨域佐证里提了一句"NSFW 调色盘"） | 用户捞回为 `probe-nsfw`，触发条件"用户主动提及时，不主动引导" | ✅ **B 独有补充**。注意 A 的 `B_SEGMENT` 发现 5 把 NSFW 列为"覆盖盲区，标注不覆盖"——B 的处理更积极且有 V3 依据（"传统 NSFW 写法教 AI 做什么，调色盘写法教 AI 为什么做"） |

最后一条值得单独标记：**A 打算把 NSFW 写进 B 段作为"不覆盖"声明，B 打算把它做成一个 probe 文件。这是 A 的一条待落盘结论会被 B 直接推翻**，融合时要记得回头改 A 的 §八 产物 3。

## M9 案例库时机 🔴

**A**：`case-library.md` 是 11 个 reference 之一，阶段 2 就要写；A1 段要保留 2-3 个追问回合的原始对话片段（"A1 是 case study 不是 testimonial"，三方一致）。但 A1 决策 1/2/3/4（条数 / 姜糖入选 / 三明月入选 / 对话片段幅度）全是 🔴 待决策。

## M10 快速路径 ✅

**A**：§十三 G1-G9 全套定稿——本质（能力问题不是意愿问题）/ 切换条件（连续卡住即切，不追问原因）/ 五步流程（基础信息→小传→采访→情绪阈值→意象，每步有追问动作和完成标准）/ MVC 锚点（情绪阈值后意象前 + 一致性检查）/ 双向性 / 标签优先 / 引导升级阶梯 / 示范边界 / 情绪串防御性纠偏。

## M11 确认信号 vs 质量门 ✅

**A**：用户确认信号 6 类——正面认可 ✅ / 补充确认 ✅ / 修正确认 ✅ / 沉默不反对 ❌ / 模糊敷衍 ❌ / 诱导性确认 ❌，加防作弊三条（确认前必须展示行为级内容、禁止诱导性提问、敷衍触发追问）。判的是"**用户认不认可 AI 的提炼**"。

**B**：每个追问动作一个质量门。例：泛化检测的质量门是"用户的回答能让 AI 看到一个具体画面，不再是形容词堆砌"；矛盾检测是"用户给出了两个标签共存的内在逻辑，或修正了不准确的标签"。判的是"**用户的回答质量够不够、能不能推进**"。

**判定：✅ 两个不同的判断，互补，都要。**

A 缺逐动作质量门（A 只有一条通用的衍生合格标准："场景+动作，无纯形容词，无解释词"），B 缺确认信号定义（B 完全没有"什么算用户认可、敷衍算不算"）。

融合方向：合并进一个 reference，命名从"确认信号"扩为"推进判据"——包含两部分：逐动作质量门（这一轮问够了没）+ 确认信号定义（用户对提炼的回应算不算数）。

## M13 skill 命名与产品定位 🔴（应最先拍板）

场上有**三个名字**指向同一个东西：

| 名字 | 出处 | 状态 |
|---|---|---|
| `char-build-guide` | A 套全套文档 | 设计中，未落地 |
| `char-builder` | B 套 `ARCHITECTURE_DECISION.md` 的目录名 | 设计中，未落地 |
| `char-creator` | ① B 套 `PIPELINE_STATE.md` 的标题："性格调色盘 → char-creator skill"<br>② **已经装好的** `.claude/skills/char-creator/`（SKILL.md + 8 references + templates） | ①设计中 ②**已存在且可运行** |

**这不是命名问题，是产品定位冲突：**

- **A 的立场 = 并存新建**。A2 审查把 char-creator 当作**兄弟 skill**处理：Agent 2 把"char-creator 已存在"列为误触发热点 2，要求 char-build-guide 的 description 在措辞上避开 char-creator 已占位的"创建角色 / 设计人设 / 写角色卡"。A2 决策 2（🔴 待拍板）就是"完全避词 vs 保留+区分"。
- **B 的立场 = 改造替换**。B 的 PIPELINE_STATE 标题直接写"性格调色盘 → char-creator skill"，B 的追问动作 #7 引用"已有 char-creator **雏形**的第零步"——把现有 skill 当作要被本次蒸馏产出取代的原型。

## M14 决策记录规范 ✅

**A**：§〇 每条决策必须回答 5 问（做什么 / 怎么做 / 为什么 / 代价 / 不要怎样做）+ 三条铁律（被否决方案必须记录、被取代的决策不删除、推理链必须保留）+ 四档状态标记（✅ 已确认 / 🟡 待确认 / 🔴 待决策）。

**B**：`ARCHITECTURE_DECISION.md` 的结构是"最终架构 / 为什么是这个架构 / 决策过程 / **被否决的方案和原因**（表格）/ 接手 AI 的行动指南"；`DIAGNOSTICS_DECISION.md` 有"决策过程 / 各 agent 的独特贡献 / 接手 AI 的行动指南"。

**判定：✅ 实质等价，A 更严格。**

B 有的：结论、依据、被否决方案+原因、接手指南。
B 缺的：**决策状态标记**（B 的所有决策都是平铺的，看不出哪些用户拍过板、哪些是 agent 建议）、**"被取代不删除"的铁律**、**代价一栏**（B 的 ARCHITECTURE_DECISION 有"独立文件的弊端（已评估，认为可接受）"，但不是每条决策都有）。

融合方向：统一用 A 的 §〇 规范；B 的存量决策补两样——状态标记（哪些是用户拍板 vs agent 结论）和代价栏。B 的"各 agent 的独特贡献"表值得反向输出给 A，A 的审查报告里 agent 贡献是散落的。

## 附：两套方法论经验的互补（不是冲突，但值得记）

| 经验 | 来自 | 内容 |
|---|---|---|
| **两轮对照法** | A §12.7 | 第一轮批判 agent + 第二轮辩护 agent。教训："单轮共识受 prompt 立场影响"——第一轮 prompt 里"早期设计"四个字暗示了过时，导致 3 个 agent 集体倾向推翻。**结论必须两轮对照才可靠。** |
| **不塞方案给 agent** | A §12.8 审阅过程 | 用户纠正："不要把你的方案给 agent，让 agent 自己思考"。第一批 3 个 agent 带了主流程方案预设立场，产出被污染；第二批不塞方案、三个不同角度，产出质量明显更高。 |
| **跨模型多样性** | B DIAGNOSTICS | 诊断判据用了 3 个模型家族的 5 个 agent（deepseek-v4-flash / hy3 / glm-5.2 ×3）。"三级判定"是 5 个 agent 不约而同提出的——**跨模型的不约而同比同模型的多数票更有说服力**。A 套几乎全用 glm-5.2。 |

三条合起来是一套完整的 agent 使用纪律：**跨模型 + 不塞方案 + 两轮对照**。后续派发子任务时应同时满足这三条。
