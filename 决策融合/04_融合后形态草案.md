**每个 probe 文件的强制结构**（A7 确认项）：

```markdown
## AI 内部诊断     ← 用户看不到。什么情况该用这个动作
```

前三节是 B 的原设计，第四节是用 A 的 53 条反例补的——B 的 probe 现在只说"该怎么做"，不说"什么算做错了"。

## 四、这份草案暴露出的两个新问题

写草案时发现的、两套都没处理的问题，记下来避免遗忘：

**问题 1：`route-logic.md` 过载了。**
它现在装着多入口路由 + MVC + 降级链条 + 卡住根因诊断 + 引导升级阶梯 + 示范边界 + 方向变更处理——七件事。按 B 的"一对一映射"原则，这是典型的"打开文件找章节"，正是 B 否决过阶段合并方案的理由。
**建议**：拆成两个——`route-logic.md`（入口路由 + MVC + 方向变更，即"往哪走"）和 `stuck-handling.md`（降级链条 + 根因诊断 + 升级阶梯 + 示范边界，即"卡住了怎么办"）。后者的触发条件极清晰："用户卡住时"。拆完 references 变 17 个。

**问题 2：「基础身份」没有 probe。**
B 的五阶段里有"基础身份（轻量）"，A 的 ARCHITECTURE 内部模式里有"基础信息模式"，但**两套都没有一个基础信息的追问动作定义**——A 只在 G3 快速路径第一步给了"遮名测试/删行测试/画面替换/性格标签混入时截断"，那是快速路径专用的。深入模式的基础身份怎么追问，是空的。
**建议**：新增 `probe-identity.md`，内容从 A 的 G3 第一行 + 教程 0 号提取。拆完 references 变 18 个。
