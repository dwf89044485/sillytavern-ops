## P0 · 致命缺陷（不改 skill 无法正确工作）

### P0-1. 二次解释的生成时机与 MVC 定义存在内部矛盾 `[!]`

**三个来源互相打架：**

- handoff §2.6 表格把「二次解释」列为必须步骤，排在 MVC 之前
- handoff §2.21 定义 MVC = 调色盘 + 二次解释，MVC 在条件步骤前触发
- handoff §2.13 明确说"组装阶段统一生成所有二次解释条目……调色盘完成前无法可靠判断，混色完成前对'情绪不稳定'类误读无法全面覆盖。组装时有了完整的调色盘（含条件步骤的结果），一次性过一遍最可靠"

**三者无法同时成立。** MVC 需要二次解释才能成立，但完整的二次解释需要混色+多面性+核心人格层完成后才能生成——这些恰好在 MVC 之后的条件步骤里。

**当前 SKILL.md 试图调和**：把二次解释放在步骤 2，但标注"组装阶段统一生成"。这个标注是对的（和 §2.13 一致），但位置是错的——它出现在 MVC 之前，而实际生成要等到条件步骤之后。AI 读到这个会困惑：现在写还是等会儿写？

**教程原文不支持 handoff 的"二次解释必须在组装阶段"这个判断。** 教程 #1 第四节（作者的二次解释）里的示例——"关于假小子与外貌""关于大大咧咧的本质""关于乐观的双重性"——这些二次解释条目完全可以基于调色盘+素材就写出来，不需要等混色/多面性。教程并没有规定二次解释必须在所有构件完成后才生成。

**但教程也没有说二次解释只写一次就够。** 教程 #4 第七节（混色和二次解释的关系）明确指出：混色画面写完后，二次解释需要追加新的防误读条目（"关于她的生气：溢出来的形状是生气，里面可能是疲惫、委屈、恐惧"）。教程 #7 第十四节也有类似补充。

**cangjie 没有直接约束这个问题**，但 cangjie 的 RIA++ 框架要求 E 段有明确的判停点——如果二次解释分两次生成，每次的判停点必须说清楚。

**推荐决议**：二次解释分两轮，不是一次。

| 轮次 | 时机 | 覆盖范围 | 判停点 |
|------|------|---------|--------|
| 第一轮 | 调色盘完成后 | 调色盘衍生中最基本的误读方向（"安静≠冷漠""嘴硬≠傲娇"） | MVC 决策点的前提 |
| 第二轮 | 组装阶段（条件步骤全部完成后） | 混色引发的误读（"矛盾情绪≠情绪不稳定"）、核心人格层引发的误读（"防御机制≠性格标签"）、多面性的语料混淆 | 一致性验证的一部分 |

MVC 定义保持"调色盘 + 二次解释（第一轮）= AI 已能基本正确演绎"。第二轮是深化。

- [ ] **待修复**

### P0-2. test-prompts.json 完全缺失 `[!]`

**cangjie 质量红线第 4 条**（硬性门槛）："每个 skill 必须有 test-prompts.json，且包含诱饵测试（不应调用的场景），其中至少 1 条是同书兄弟 skill 的场景。"

**cangjie 阶段 4**："只测 positive case，skill 总会看起来'很好'，但实际部署后会乱激活。"

**handoff 未涉及测试**——handoff §3（已创建文件清单）和 §6（待补充项）都没有提到测试。这是 handoff 的设计缺口，cangjie 补上了。

**当前 char-creator 没有任何测试用例。** 你无法回答这些问题：
- 用户说"帮我分析一下这个现有角色的性格有没有问题"→ 应该触发 char-creator 还是诊断类 skill？
- 用户说"用她的语气写一段她第一次见到 {{user}} 的场景"→ 应该触发 char-creator 还是写作类 skill？
- 用户说"帮我润色这段角色设定"→ 应该触发 char-creator 还是编辑类 skill？

**需要至少 8-12 条测试用例**，覆盖 should_trigger / should_not_trigger / edge_case / 兄弟 skill 混淆四种类型。

### P0-3. 问题目标层缺失——AI 会为问而问，不收敛 `[!]`

**handoff §2.16**（2026-08-05 专门补丁）：在动机追问之上必须补一层"问题目标层"——告诉 AI 每个问题在探什么、探到什么算够。handoff 的原话警告："一个只读 skill 文档的 AI 知道要问具体问题，却不知道每个问题在探什么、探到什么算够，会把问法六类当菜单轮着用，永远不收敛——为问而问。"

**cangjie 阶段 2 E 段**要求："每一步有可判断的完成标准"——隐含了同样的要求。

**教程 80 问**提供了完整的支撑素材：
- 十组目标（"这一组解决的是：角色核心 / 调色盘 / 背景来源 / 欲望缺失恐惧 / 防御决策 / 关系 / 三面性 / 混色 / 台词行为 / 底线弧光二次解释"）
- 下钻五连问（标签→具体做什么→什么时候→为什么不直接说→会伤到谁→什么时候停下）
- 核心人格层终点清单（"最低限度要知道：她在什么瞬间会做决定……"）

**当前 questioning-strategies.md 只有"怎么问"（六类问法+例句），完全缺失"问什么目标"这一层。** SKILL.md 问法策略段也没有提示 AI "每个问题心里要有目标"。

- [ ] **待修复**

### P0-4. R 段（原文引用）完全缺失

**cangjie 质量红线第 2 条**：每个 skill 必须有完整的 R/I/A1/A2/E/B 六段。R 段要求"直接引用 ≤150 字/段，必须标注出处"。

char-creator 的 references 正确转述了教程概念，但**没有任何原文引用，也没有出处标注**。教程里有一些应该作为 R 段被保留的金句：
- "AI 生成文本的本质是联想词——你给的内容越具体、越私人，AI 接出来的内容就越不像 AI。"（教程 #11）
- "衍生就是一个超级压缩包。你写三到五条衍生，AI 解压出来就知道'哦，自卑在这个人身上是这个味道的'。"（教程 #10/02）
- "把看似矛盾的两个东西放在同一条衍生里，这是只有人类作者才能做到的事。"（教程 #1）

**R 段的作用**（cangjie §阶段 2）：给 agent 建立权威性——"这个规则不是我编的，是教程作者说的"。没有 R 段，agent 在用户质疑"为什么要这样做"时只能回答"skill 这么写的"，不能回答"教程作者发现这样做效果最好"。

**注意**：R 段不需要全塞进 SKILL.md。按 cangjie 实践，可以放在 references 文件里（每条规则标注出处），SKILL.md 只保留最核心的 1-2 条引述。但必须有，且可追溯。

- [ ] **待修复**

### P0-5. A1 段（教程案例）完全缺失

**cangjie 质量红线第 2 条**：A1 段要求"作者在书中亲自用过的具体案例，至少 1 条，≤3 条，每条要点明：遇到什么问题 → 怎么用这个方法 → 得出什么结论"。

**cangjie §阶段 2 原文**："这一段的作用是让 skill 在被调用时，agent 有具体的类比素材可用。"

教程里有大量作者亲用的完整案例，当前完全没有被 skill 利用：

| 案例 | 用什么技法 | 适用场景 |
|------|-----------|---------|
| 秋明月 | 调色盘 + 三面性 + 混色 + NSFW 调色盘 | 复杂角色全栈 |
| 红美铃 | 调色盘 + 三面性（坏女人型） | 防御机制为毒舌/控制 |
| 陈乖乖 | 调色盘 + 三面性 + 混色 + 核心人格层 + 意象（晴空柚子 7 章） | 完整流程示范 |
| 姜糖 | 调色盘 + 混色 + 两面性 + 意象 | 极端角色（丧失语言能力） |
| 洛潮汐 | 混色 20 个画面 | 混色密集示范 |
| 姜渡 | 台词人设 | 克制型模型替代方案 |
| 三明月 | 基础信息 + 小传 + 采访 + 喜怒哀乐衰 + 意象 | 入门平替路线 |

**没有 A1 段的具体后果**：当一个 agent 在构建过程中遇到"用户给了一个混色画面但我不知道够不够好"的情况时，它没有参照物。如果 A1 段里有"洛潮汐的混色画面长这样"，agent 就可以对标判断。

**推荐做法**：不把完整案例塞进 SKILL.md（那太重）。在 `references/` 下新增一个 `case-studies.md`，选 3 个类型差异最大的案例（一个复杂全栈如陈乖乖、一个极端角色如姜糖、一个入门平替如三明月），每个精简到核心技法应用+关键产出片段。SKILL.md 的 A2 旁边加一句"类比素材见 `references/case-studies.md`"。

- [ ] **待修复**

## P1 · 重要缺陷（skill 能跑但质量受损）

### P1-1. A2（trigger）语言信号过窄

**cangjie §阶段 2 A2** 要求"语言信号建议中英双写关键 trigger 词"。

当前 description：
```
Character creation collaborator — helps a human author build an AI-playable character
through guided conversation. Use when the user wants to create a character, design a
persona, build a character card, or explore who their character is.
```

问题：
- **全是英文。** 用户说"帮我写个角色""我有个角色想法""帮我设计个人物"时，纯英文 description 触发概率降低
- **缺少"不应触发"信号。** "用户说'帮我写个角色'但意思是让 AI 直接生成一张卡"——这和 skill 的"人机协作构建"是两回事。description 没有区分这两种场景
- **缺少与相邻 skill 的区分。** cangjie 要求 A2 写"和哪些相邻 skill 不同"

**注意**：handoff §2.1 说"description 不需要做触发优化"——但这个决策的前提是"用户主动使用本技能"。实际运行中，用户不一定记得 skill 的名字，他们可能说"帮我设计角色"然后期望系统自动匹配。而且即使手动触发，一个精准的 description 仍然有助于 agent 在被调用后正确理解自己的任务边界。

**推荐**：description 中英双写，加一句"NOT for generating a character card directly without user collaboration"。

- [ ] **待修复**

### P1-2. I 段（自述）写成操作手册而非方法论重述

**cangjie §阶段 2 I 段**要求："用你自己的话重写方法论的核心骨架。读完这段，一个没读过原书的人能否理解这个方法论在做什么？若不能，重写。"

当前 SKILL.md 的结构是：
- 红线（1 条原则）
- 你的角色（身份定义）
- 入口引导（操作步骤）
- 问法策略（操作规则）
- 三层交互模式（操作规则）
- 构建流程（操作步骤）
- 交互原则（规则清单）
- 禁止事项（规则清单）

**这是一个操作手册的结构，不是方法论重述的结构。** 一个没读过教程的 agent 读了这份 skill，知道"要追问行为""要写衍生""要推演候选"，但不知道**为什么这套方法有效**——为什么"写行为不写标签"能让 AI 演得更像活人？为什么"从素材里提取颜色"比"直接贴性格标签"好？

缺失的这一层会导致：当对话偏离 skill 预设的路径时（比如用户给了一个非常特殊的角色类型），agent 只会机械执行规则而不会基于方法论原理做判断。

**教程里有明确的"为什么"层**：AI 是联想词引擎（教程 #11 第一章）、标签化的问题是"频道切换"而非"融合"（教程 #10/02）、活人感来自低频关联偏离数据库默认（教程 #1 第一节）。

**推荐**：SKILL.md 开头（红线之前）加一个"## 核心洞察"段，用 ≤10 行把教程最关键的 3 个底层原理写清楚。不展开，但必须让 agent 知道"为什么"。

- [ ] **待修复**

### P1-3. B 段（边界）不完整

**cangjie §阶段 2 B 段**要求包含三层："什么时候不要用 + 作者警告过的失败模式 + 容易混淆的相邻方法"。

当前 SKILL.md 有"禁止事项"——覆盖了"不要做什么"，但缺：

**a) 教程作者警告过的失败模式：**
- 教程 #6 结尾"你自己得先被你的角色打动"——这不是鸡汤，这是边界。如果用户对角色无感，skill 应该识别并引导，而不是硬推流程
- 教程 #3 警告"台词人设和调色盘不混用。一个角色要么用调色盘写，要么用台词人设写"——skill 如果不认识这条边界，可能在调色盘流程里混入台词人设技法
- 教程 #1 警告"AI 一旦参与创作……在 AI 扮演中劣化最严重"——如果用户要求 AI 直接扩写衍生，skill 应该拒绝而不是照做

**b) 与相邻方法的混淆：**
- "帮我写个角色"但用户意思是"AI 直接生成完整角色卡给我"→ 这不是 char-creator，这是"角色卡生成器"
- "帮我看看这个角色的性格有没有问题"→ 可能是诊断而非构建
- "用她的语气写一段试玩"→ 这是扮演/写作，不是构建

**推荐**：在 SKILL.md 禁止事项后加"## 边界（什么情况不该用我）"段，包含教程作者的警告和相邻场景区分。

### P1-4. E 段完成判据未显式标注

**cangjie §阶段 2 E 段**："每一步有可判断的完成标准。如果有判停点，显式写出。"

当前 SKILL.md 隐式存在但未显式标注：
- 素材收集的完成判据：SKILL.md 三层模型写了"最近 3 轮没有新的行为场景或关系细节 → 进入脚手架"，但这是模式切换判据，不是"素材收集步骤完成"的判据
- 调色盘的完成判据：没有写。handoff §2.21 的 MVC 标准（"底色和主色已定，颜色都是行为描述"）不在 SKILL.md 里
- 脚手架的判停点：写了（2 次被否 → 进入推演），但推演的判停点是"用户裁决"——没有说裁决后如果用户全否了怎么办

**cross-check 教程**：80 问结尾的检查清单——"我是不是只写了标签没有写行为？我是不是把背景写成了全部解释？"——这本质上就是完成判据，但 skill 没有把它做成可操作的检查点。

**推荐**：在构建流程的每个步骤后面，加一句"✓ 完成标准："。不要写长篇，就一行。

### P1-5. 推演工具箱缺失扩展池和选择规则

**handoff §2.11 定义了完整的推演框架**：核心四框架（依恋/防御/社会学习/认知图式）+ 扩展池（8 个按角色类型触发）+ 选择规则（每轮从核心四挑 2-3 + 扩展池加 1 个，挑结构性差异最大的）。

**当前 palette.md 只有核心四框架的一行描述**，缺失：
- 扩展池（创伤/应激反应 / 家庭系统 / 存在主义 / 社会角色印象管理 / 自我决定理论 / 发展任务 / 荣格阴影 / 情感调节）——每个只需一句话机制+触发条件
- 选择规则（"不是全部推一遍，挑差异最大的 2-3 条"）
- "框架是后备，主引擎是从素材里面抓重复模式"的原则说明

**cangjie 没有直接约束这一点**，但 cangjie 的多框架并行提取（阶段 1 的 5 个 extractor 各从一个视角提取）和 handoff 的多框架推演在设计理念上是一致的：多样性不靠灵机一动，靠从不同生成轴推演。

**推荐**：`palette.md` 尾部加"## 扩展工具箱"段（核心四框架完整描述 + 扩展池触发条件 + 选择规则），不要超过 40 行。

### P1-6. V2 预测力风险——对简单角色的判断未经教程验证

**cangjie 阶段 1.5 V2 预测力测试**："能用这个方法论去分析一个书里没讨论过的场景，得出有意义、非平庸的结论吗？"

教程的案例池有一个偏向：**所有深度示范案例都有内心矛盾、都有防御机制、都适合深挖。** 教程 #2（三面性）和 #4（混色）都说了"不是所有角色都需要"，并且给了判据，但教程本身没有用一个"就是一只快乐小狗"的简单角色来完整走一遍流程，示范"在哪些地方停下来"。

**风险场景**：用户想创建一个生活单一、性格一致、没有内部矛盾的角色。MVC 应该在这里触发并且停下。但如果 agent 没有足够的类比素材（回到 P0-5 A1 缺失），可能误判为"素材不够，继续追问"——永远不会收敛，因为简单角色就是没有那么多素材。

**handoff 的 MVC 机制部分覆盖了这个问题**，但 MVC 判据偏抽象（"底色和主色已定，颜色都是行为描述"），没有简单角色的具体判据。

**推荐**：在 `palette.md` 或 MVC 相关段落里加一条："如果经过 3 轮追问，用户能给出的行为场景都集中在同一个维度（如'她就很快乐'的各种表现），没有内部矛盾、没有压力切换、没有两种颜色碰撞——这就是 MVC 完成的信号，不是素材不够。"

- [ ] **待修复**

### P1-7. 镜像/具象追问的"追问铁律"与脚手架模式有隐藏冲突

SKILL.md §问法策略写了"追问铁律：只问，不给方向。不暗示"。但三层交互模式里的"脚手架"的定义是"给一个试探方向"（"我猜个方向你看对不对"）。

**这两个指令在同一个 skill 里但不是同一个模式**：追问铁律适用于镜子模式，脚手架模式是故意给方向来激发反应。但 SKILL.md 的表述没有显式标注这个切换——AI 可能在镜子模式里忍不住给方向，也可能在脚手架模式里不敢给方向。

**推荐**：追问铁律加限定词"在镜子模式下"，脚手架描述强调"此时给方向是合法的——但方向只能从已积累素材里提取，不涉及未确认维度"。

- [ ] **待修复**

## P2 · 次要缺陷（体验/鲁棒性）

### P2-1. 标签下钻五连问未嵌入问法流程

**教程 80 问**：用户给标签 → 追问五连（具体做什么→什么时候→为什么不直接说→会伤到谁→什么时候停下）。

**handoff §2.16** 将它列为"够不够的判据"。

当前 `questioning-strategies.md` 具象类只写了第一步（"她是做了什么让你觉得温柔？"），没有展开后续四步。SKILL.md 问法策略段也没有提"标签要下钻到行为层才算够"。

**推荐**：`questioning-strategies.md` 具象类部分补下钻五连。SKILL.md 问法策略的"纯标签→追问行为"改为"纯标签→下钻五连，直到能落成一句行为描述"。

- [ ] **待修复**

---

### P2-2. "一次一个问题"与脚手架模式冲突

SKILL.md §交互原则写了"一次一个问题"。但脚手架模式说"我换个方式——我猜个方向你看对不对"——这是一句话的方向试探，不是问题。严格执行"一次一个问题"会迫使 agent 把方向试探拆成一个提问，丧失脚手架的效率。

**推荐**：改为"一次一个交互单元"——可以是问题、方向试探、或推演候选组。

- [ ] **待修复**

---

### P2-3. 入口引导第三步缺少"先总结记录再追问"

**handoff §2.9 第四步**："用户说完了，AI 总结记录，再按内容选方向追问"。

当前 SKILL.md 第三步写的是"先完整听，不打断，不引导。用户说完了再按内容类型追问"——缺失了"先总结记录"这一步。不在追问前记录，多轮后原始内容会丢失。

**推荐**：第三步末尾加"听完了先把你听到的总结记录到素材区对应小节，再追问"。

- [ ] **待修复**

### P2-4. MVC 告知文案用术语

SKILL.md MVC 段写："可以看看效果（文档不是运行时格式，后续需提炼）"。

"运行时格式"是术语，用户听不懂。**handoff §2.17 做了产物名翻译（调色盘→性格质地），但没有翻译这个。**

**推荐**：改为"人物文档和最后放进世界书的角色卡是两回事——世界书里的卡要极致压缩，删掉 AI 已知的默认值和推演因果链。现在可以先看看效果"。

- [ ] **待修复**

---

### P2-5. 反模式诊断未嵌入流程检查点

`anti-patterns.md` 写了 6 类诊断，但 SKILL.md 没有说明何时加载它。按 cangjie 阶段 4 思维（在输出前做检查），以及 handoff §2.19c（推演后交叉检查），**应该在两个时机触发**：
1. 推演完成后、给用户看之前（交叉检查）
2. 用户反馈"感觉不对"时（诊断）

当前只在 SKILL.md 禁止事项里散落了一些（"衍生/推演出形容词""用户用极度极致→拦截"），没有形成系统性的"推演后自查"步骤。

**推荐**：SKILL.md 构建流程推演段加一句"每次推演完成后、给用户看之前，过 anti-patterns.md 自查"。

- [ ] **待修复**

### P2-6. 世界设定缺少显式记录动作

**handoff §2.9**："世界设定记入素材区（作为角色的背景上下文）"。

SKILL.md 第一步只说"按需聊到能支撑角色构建即可"，没有说"记入素材区·身份下的世界设定"。

**推荐**：第一步末尾加"聊完记入素材区 → 身份 → 世界设定"。

- [ ] **待修复**

---

### P2-7. references 之间缺乏输入输出契约

**cangjie 的原子化设计理念**：每个 skill 独立可调用，互不干扰。char-creator 作为一个 skill 不需要拆成多个，但 references 之间应该有清晰的"输入→输出"契约。

当前状态：`palette.md` 说了怎么从素材提取颜色，但没有说它的输入是什么格式（素材区的小节结构）、产出写到文档的哪个位置。`core-layer.md` 说了七元素，但没有说它的前置依赖是什么（需要调色盘已定？需要素材区相关经历？）。

**后果**：agent 在加载单个 reference 时，不知道这个 reference 的前提条件是什么，可能在不合适的时机调用。

**推荐**：每个 reference 开头加一行"前置条件"（如 `palette.md`："前置条件：素材区有 ≥3 条非标签化的记录"），末尾加一行"产出写入"（如："产出写入 → 人物文档·构建区·性格质地（调色盘）"）。

- [ ] **待修复**

### P2-8. handoff 缺少安装/交付步骤

**cangjie §阶段 5**："询问用户安装位置，把通过测试的 skill 复制或 symlink 过去——没有这一步，产出的 skill 无法被真正调用。"

handoff 的"已创建文件及状态"（§3）和"下一步计划"（§4）都没提安装。char-creator 已经放在 `.claude/skills/char-creator/` 下，实际上是已安装状态，但在设计流程里没有"交付"这一步的意识。未来 skill 迭代完成后，如果改了目录结构，没有交付步骤可能导致旧版本残留。

**这不影响当前功能，但作为 skill 制作流程的完整性缺口，应该记录。**

- [ ] **待修复（低优先级）**

## P3 · 打磨项

### P3-1. SKILL.md 可加"核心洞察"段提升 AI 理解深度

P1-2 说了 I 段问题——当前是操作手册而非方法论重述。修复方式是加一段"核心洞察"，≤10 行：

```
## 核心洞察

AI 生成文本的本质是联想词引擎——你给的上下文越像数据库里的常见模板，AI 的输出就越刻板。
活人感来自**偏离数据库的高频关联**：把"自卑"和"社交达人"放在同一个人身上，
把"笑着说别走"和"手没有松开门把手"放在同一个动作里——这些低频但真实的组合，
AI 不会主动联想。你的工作就是创造这些偏离。

为什么我们追问经历而不是性格标签？因为经历是具体的（"爸爸10岁去世"），
标签是抽象的（"极度自卑"）。AI 从经历里能长出无数种性格可能；
从标签里只能长出数据库里最常见的模板。
```
